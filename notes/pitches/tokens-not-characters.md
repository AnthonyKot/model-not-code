# tokens-not-characters — pitches (2026-09-12)

**Working title:** Why the Model Cannot Count the Letters in “Strawberry”
**Mechanism (catalog):** Byte-pair merges map text to integer IDs from a fixed table; tokens, not characters, are the unit of cost, context length and many errors.

## Pitch A — the model never saw the letters

You ask a model to count the letters in a word, it gets the count wrong, and you file the result under "not as clever as advertised" when the real cause is that no character ever reached the network: the input was a short list of integers, each standing for a chunk of text chosen before training by a merge procedure. The essay explains that procedure step by step — start with single characters, count every adjacent pair across a corpus, merge the most frequent pair into one new symbol, repeat for a fixed number of merges, then encode new text by replaying the merge list in order — and shows why a common word becomes one integer whose spelling the network can only learn indirectly, from whatever the training text happened to say about it. The worked example (invented) is a four-word corpus — "sun" ×4, "sung" ×3, "gun" ×2, "gong" ×1 — on which the first merge is `u`+`n` (count 9), the second `s`+`un` (count 7), the third `sun`+`g` (count 3), so that after three merges "sung" encodes to one ID, "gun" to two (`g`, `un`), "gong" to four, and a word the corpus never held, "snug", falls back to four single characters; every pair count is on the page for the reader to re-tally. The exercise is a byte-pair trainer in about thirty lines of any language, run first on the toy corpus (expected: exactly those three merges in that order) and then on a page of the reader's own prose for 200 merges, where the expected result is that the earliest merges are letter pairs and common short words, that a proper noun from the page splits into several pieces, and that the reader can now say for any word how many integers the model actually received.

## Pitch B — the bill and the window are counted in tokens

You size prompts and budgets in characters or words, and then a conversation that felt short overruns the context window, or the invoice is several times the number you estimated from the last message alone. The essay explains that the model call is stateless, so every turn resends the whole exchange so far as one flat sequence of token IDs, that generated tokens are appended to that same sequence one at a time and must also fit, and that the unit the provider meters and the window bounds is the token, whose ratio to characters is roughly four to one for ordinary English but tighter for code, numbers and rare names (as reported in the lecture: about three-quarters of a word per token, and a decimal expansion split into three-digit chunks). The worked example (invented) is a chat with a 40-token system prompt, 20-token user turns and 80-token replies: the input for turn k is 40 + 20k + 80(k − 1), so turns one to five cost 60, 160, 260, 360 and 460 input tokens — 1,300 in total against the 100 you would have guessed from the user's words — and with a 1,000-token window the tenth turn (960 in plus 80 out) no longer fits, all of it recomputable from the three sizes. The exercise is a token-budget function that takes a list of (role, text) turns, estimates tokens with the four-characters rule, and prints per-call input, cumulative input and the turn at which a chosen window overflows; the expected result on the essay's five-turn transcript is the sequence above, and on the reader's own log the discovery that the running sum grows with the square of the turn count, which is why a long agent loop is expensive in a way a long program is not.

Draws on: course-6100015/01-30, course-6100015/01-31, course-6100015/01-32; supporting book: *LLM Deep Dive*.

## Pitch C — the table belongs to the model, and the chat format is just more entries in it

You hand-assemble a prompt string for an instruct model, or count tokens with one model's tokenizer and serve another, and the output rambles or the budget is off, because you treated "the tokenizer" as a shared standard when it is a per-model table with a few reserved rows whose meaning is nothing but a training-data convention. The essay explains the table — ordinary entries produced by merges, reserved entries for begin-of-text and role markers, an integer for each — and shows that a chat is not a structured object the network receives but one flat sequence in which those reserved integers are interleaved with the text, that the same sentence maps to different integers and different lengths under two tables, and that the final marker for "assistant turn starts here" is what makes the next predicted token an answer rather than another question. The worked example (invented) is two eleven-row tables: under table A the text "hi there" encodes to two IDs (5, 6) and under table B to three (0, 1, 2); decoding B's integers with A's table yields "<bos><sys><eot>", three control markers and no words, and rendering a three-message chat with A's markers costs six extra tokens per exchange before any text — overhead the reader can count and must budget. The exercise is `encode`, `decode` and a small `render_chat` over the two toy tables, with a test that decodes each table's output through the other; the expected result is the garbage above on the cross-decode, a fourteen-integer sequence for the example chat, and the ability to look at any provider's documented special tokens and say which integers in a request are text and which are convention.

Draws on: course-6100015/03-11, course-6100015/03-12, course-6100015/03-13, course-6100015/03-14, course-6538601/03-02; supporting book: *LLM Deep Dive*.

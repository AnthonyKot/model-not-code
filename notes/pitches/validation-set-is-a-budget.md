# validation-set-is-a-budget — pitches (2026-09-12)

**Working title:** You Only Get to Look at the Test Set Once
**Mechanism (catalog):** Train, validation and test are three budgets; the validation curve picks the checkpoint, and every look at the test set spends it.

## Pitch A — selection is a kind of training

The number you reported to the team was the best validation score across every checkpoint and hyperparameter you tried, and the model in production is scoring lower than that number, because choosing the winner by a noisy measurement biases the measurement upward. The essay explains one mechanism, the winner's curse on a held-out set: a validation score is the true score plus sampling noise, picking the maximum of several such scores picks the noise as much as the model, and the only estimate that is not biased by your choices is one made on data that played no part in any choice — which is what the third split is for, and why fitting the normaliser on the training rows alone is the same rule applied earlier. The worked example (invented, small) has six checkpoints that are all genuinely 50% accurate and a validation set of twenty items; the reader recomputes that one checkpoint scores 13/20 or better in about 13% of cases for a single checkpoint and in about 57% of cases for the best of six, so "65% on validation" is the expected outcome of picking, and the fresh test set returns 10/20. The exercise needs only a coin or `random.random()`: simulate eight fair-coin "checkpoints" on 200 validation flips each, report the best one's accuracy, then re-score that same checkpoint on 200 new flips; the expected result is that the reported best sits a few points above 50% and the re-score falls back to it, with the gap shrinking as the validation set grows.

Draws on: course-4735368/03-09 (why evaluating on seen data overestimates; splitting by ratio; normaliser fitted on train only), course-6100015/07-20 (picking the best checkpoint on validation "is a kind of training", so test must stay separate; "lucky with random noise"), course-6100015/07-19 (a good training loss is not a good eval loss). Supporting book: Huyen, *Designing Machine Learning Systems* (data leakage and splitting).

## Pitch B — the curve is a stop signal you have to read

Your training loss went down for every epoch and the model got worse after epoch two, and nothing in the training log told you, because the training loss cannot see overfitting — only a held-out curve can. The essay explains the validation curve as the one instrument that separates "still learning" from "memorising": what the per-epoch validation loss measures, why it turns while training loss keeps falling, and how three rules read it — save-best-only checkpointing (keep the weights at the lowest validation loss), early stopping with a patience and a minimum delta, and a learning-rate drop when the curve stalls — each stated as a small decision procedure, with the lecture's reported case (an eval loss that fell across two epochs and jumped back near its start at the opening of the third) as the shape to recognise. The worked example is an invented table of eight epochs with training loss falling monotonically from 0.90 to 0.31 and validation loss 0.80, 0.62, 0.55, 0.53, 0.56, 0.61, 0.70, 0.84; the reader applies patience 2 and min_delta 0.01 by hand and finds the kept checkpoint is epoch 4, training stops at the end of epoch 6, and a plateau rule with patience 2 and factor 0.1 would have cut the learning rate from 0.01 to 0.001 after epoch 6 as well — so the checkpoint you ship is not the last one and not the one with the best training loss. The exercise gives the reader a second twelve-epoch table (with a false dip, one epoch that improves by less than the delta) and asks them to write the two-line early-stopping rule in any language and run it; the expected result names the kept epoch and shows that changing the patience from 2 to 4 changes which checkpoint is kept, which is the point: the stop rule is a hyperparameter too.

Draws on: course-4735368/07-04 (ModelCheckpoint with save-best-only on validation loss, reported 0.47 first save then 0.24 at the sixth epoch; ReduceLROnPlateau with patience, factor 0.1, min_delta), course-6100015/07-19 (eval loss reported 1.27 → 1.123 at step 6200, jumping to 1.283 at the start of epoch three; checkpoints saved every N steps so the best one can be picked), course-4735368/03-09 (validation data passed to training so you can stop early and adjust), course-4735368/03-10 (when both curves are high it is underfitting, a different failure).

## Pitch C — the leak happens before training starts

Your validation score was flattering from the first epoch, not because the model was good but because the preprocessing had already seen the validation rows: the normaliser's mean and standard deviation were computed on the whole dataset, so a little of the held-out data was baked into every training input. The essay explains one mechanism, leakage through fitted preprocessing: anything with parameters estimated from data — a mean, a scale, a vocabulary, a category encoder, a threshold — is part of the model, so it is fitted on the training split and applied unchanged to the other two, and the same rule scales up to "every decision made on validation is a decision the test set must not have seen". The worked example (invented) is a column of eight prices split five/three: the reader computes the mean and standard deviation from all eight and from the five training rows, then the z-score of one validation row both ways, and sees the leaked version pull the held-out point toward the centre — a small shift on eight rows that becomes a systematic optimism when the model is scored on rows that helped set its scale. The exercise is a leak audit on paper: for a pipeline the reader knows (or a provided sketch of one: scaling, tokenising, class-weight estimation, threshold picking, checkpoint selection), list each step that estimates something from data and write which split it may see; the expected result is a table in which only the training split appears in the "fitted on" column and the test split appears exactly once, in the final row, labelled "scored".

Draws on: course-4735368/03-09 (normalisation on train only, the mean-and-std leak stated explicitly; splitting 1,000 rows 80/10/10 and the reported example ratios for small versus very large datasets), course-6100015/07-20 (checkpoint selection on validation as the reason the test set stays untouched). Supporting book: Huyen, *Designing Machine Learning Systems* (leakage catalogue: scaling before splitting, duplicates, time-based splits).

Note on sources: all five cited lectures carry the material assumed. course-4735368/03-10 is about underfitting and adding capacity, not about the three splits; it supports only the "both curves high" reading of the curve (Pitch B) and would be a minor citation. course-4735368/03-09's ratio example for a very large dataset is reported as 90/10/10, which does not sum to 100; the essay should quote it as reported and not repeat it as arithmetic.

# Book20: sources mapped to engineering questions

Source inspection dated 2026-09-13. Project: *The Program Is Now a Model*, `/home/diablo/book20`.

## What this collection can support

The strongest book available in these sources is about the engineering consequences of learned behaviour: how training changes an artifact, what makes evaluation credible, and what has to remain true after deployment. The collection has enough mathematical material to explain selected mechanisms and enough operational material to connect those mechanisms to decisions a working developer faces.

The courses are useful for concrete workflows and examples of mistakes encountered during implementation. The books add material the courses sometimes omit: precise definitions, mathematical steps, data lifecycle concerns, and limits. Neither source class should be treated as automatically correct. An actual arithmetic error in the local LoRA book passage makes this more than an abstract concern.

My editorial judgment is that **data validity, evaluation, and operating the resulting system deserve at least as much attention as architecture internals**. This is a recommendation from this inspection, not an approved replacement outline.

## The questions worth building around

These are possible essay questions, not drafts or approved pitches. Each proposed reader activity would need original numbers and a checked expected result.

| Question an experienced developer can bring | What the reader should be able to do | Checked source support | Possible self-contained activity |
|---|---|---|---|
| What exactly changes when training runs? | Follow inputs through a parametrised function, loss, and one weight update. | Moroney, `OEBPS/ch01.html`, one-neuron training loop; *Why Machines Learn*, chapter 10, “What's the Delta?”; Géron provides the wider implementation reference. | Calculate a prediction, loss, and update for a small linear model, then compare learning rates. |
| Why did the offline result disappear in production? | Identify information that would not have existed when a prediction was made. | Huyen PDF 163–165; TensorFlow course 03-09, lines 110–128 and 224–227. | Audit a small table with entity IDs, event times, label times, and a fitted scaler; identify invalid split/fit operations. |
| What is the unit I must version and roll back? | Include fitted preprocessing and data/configuration provenance in the deployed artifact. | Burkov PDF 77 and 139–140; Géron PyTorch PDF 116 and 130–132; OpenShift PDF 155. | Compare two release manifests and identify why restoring only the weights cannot restore the previous calculation. |
| What does changing class weights actually change? | Distinguish changing the training objective from measuring per-class errors or selecting an operating threshold. | TensorFlow course 15-02, lines 77–100; financial-risk book PDF 192–194 supplies a separate resampling workflow. | Recompute a small weighted loss, then compare two thresholds using a supplied confusion table. Keep these as separate mechanisms if necessary. |
| Does a better score mean the change caused a better outcome? | Separate predictive ranking from the effect of an intervention. | Vaughan, *Data Science: The Hard Parts*, PDF 51–52, model-versus-intervention example. | Inspect four groups defined by score band and treatment; compare treatment effects without assuming high propensity means high benefit. |
| What can be monitored before the labels arrive? | Distinguish operational health, changed inputs, and measured prediction quality. | Huyen PDF 317–318 and 332; Géron PyTorch PDF 132. | Work through a prediction/feedback timeline and mark which metrics are available at each time. |
| Can the system create the evidence used to train its replacement? | Identify selection and exposure effects in feedback data. | Huyen PDF 323–325; the inspected explanation at 323 explicitly connects predictions to later inputs. | Trace an example in which only displayed items receive feedback, and explain what cannot be concluded about undisplayed items. |
| Did retrieval fail, or did generation fail? | Inspect context selection separately from answer correctness and support. | LLM Engineering 05-18, lines 7–23 and 50–100; 05-19, lines 119–173; translated RAG 05-09. | Score a supplied ranked list, then evaluate an answer using its retrieved evidence. Include a misleading keyword match. |
| Why is the right table value in the wrong chunk? | Preserve relationships between headers, cells, and sections during ingestion. | Translated RAG course 03-08, especially lines 3–11. | Compare flattened and structured representations of an original small table and choose what a retrieved unit must contain. |
| What does LoRA save, and what remains unchanged? | Trace the shapes and parameter counts of two trainable matrices beside a frozen matrix. | LLM Engineering 07-02, lines 59–125; Raschka PDF 141–142, with the arithmetic correction below. | Multiply a small adapter pair, add the result to a base matrix, and compare storage counts. Treat quantisation as a separate question. |
| Why can a short response wait so long? | Separate prefill, decode, queueing, and batch scheduling. | Mistral course 03-07; *Inference Engineering* PDF 64–65 and 188–190; *Hands-On LLM Serving*, `OEBPS/ch06.html`. | Step through arrivals and completions for unequal request lengths; count occupied batch slots and waiting time. |
| Where does a model's tool request become an actual side effect? | Identify the application code that dispatches actions and the permissions it uses. | LLM Engineering 02-15, lines 73–108; OWASP local v2.0 PDF 9 and 27; security playbook PDF 100. | Trace a tool request through validation and dispatch and identify which layer can reject an unauthorised action. |

These questions make a useful working spine. Attention, tokenisation, embeddings, quantisation, and reinforcement learning can then earn their places by explaining a particular problem in that spine. Their presence in a course is not, by itself, a reason to allocate an essay.

## Source issues that change how drafting should proceed

1. **The local LoRA arithmetic is wrong.** Raschka PDF 142 / printed 137 gives dimensions 25 by 50 but reports 6,250 entries. The correct product is **1,250**. With inner dimension 5, the two factor counts are 125 and 250, totalling 375. I visually checked the PDF page, so this is not merely an extraction error. The same passage has malformed matrix notation. Re-derive the pilot's example; don't copy or quietly endorse the source's arithmetic.
2. **The LoRA course is an explanation lead, not the final specification.** Lecture 07-02 describes frozen weights and two multiplied adapter matrices, then describes alpha as a multiplier. The project already notes a scaling-convention discrepancy with the paper. This inspection did not fetch that paper, so its exact convention remains a drafting check. The rank should be described as a bound, not automatically equal to the adapter dimension.
3. **The retrieval tests are proxies.** LLM Engineering 05-18 proposes keywords expected in relevant context; 05-19 describes averaging keyword reciprocal-rank results and keyword coverage. It also says most example questions were model-generated. A pilot should specify its relevance judgments and evaluation unit, include cases where keyword presence is misleading, and keep development examples separate from final evaluation.
4. **Important local editions are not final/current copies.** Huyen's PDF explicitly identifies itself as an early release; Burkov's inspected pages say “Draft”; Raschka has a dated Leanpub version; Moroney is an early release; Smolyakov is a MEAP. Their locators and limits should be recorded in eventual receipts. This inspection did not change the manifest.
5. **Some filenames misidentify the contents.** `Modern_Software_Engineering_Doing_What_Works_to_Build_Better_Software.pdf` is SHA-256-identical to the Burkov ML engineering file. The quantisation PDF's actual title is *Автостопом по Квантизации*. Don't count filenames as distinct intellectual sources.
6. **The BPE pitch still needs a real algorithm source.** The inspected LLM deep-dive passage names the method; Staron shows invoking a BPE trainer. Neither checked passage supports a complete hand-worked merge derivation. This is a specific support gap, not a claim that no such material exists anywhere in the library.
7. **Figures and formulas need a separate check.** The quantisation deck and parts of Lapan's EPUB lose equations in text extraction. A text search can locate a section but cannot validate missing mathematics. Render the relevant formulas at drafting time.
8. **Several attractive statements are too absolute.** The source passages do not justify promising that RAG ensures correctness, that clipping strictly bounds every policy update, or that batches generally cost the same as a single request. State the mechanism and its conditions, and derive a bounded example.

## What I would carry forward

For the next editorial pass, use this map to test the existing candidates against four requirements: a reader problem, one explainable mechanism, checked supporting passages, and an independent example with an answer the reader can verify.

I would prioritise scrutiny of the current outline's coverage of **leakage and feature availability; the complete versioned artifact; delayed labels and monitoring; feedback selection; and model-versus-intervention evaluation**. These are not just prospective topics from filenames: the passages above provide concrete starting points. The current Part III is labelled evaluation and monitoring, but much of its space goes to domain models; the source collection can support more actual monitoring work.

LoRA remains a viable pilot. Its value would be to make the matrix update calculable and its savings precise, with a clear limit on what the example proves. The new source findings argue for a more carefully grounded pilot, not for abandoning it. No author pitch selections have been inferred from this report.
